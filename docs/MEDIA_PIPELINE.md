# 实时人物变大 / 人体内部透明：分析与处理

## 1. 两个问题，不应混在一起调参

### A. 人物在视频里变大（构图漂移）

`Stage.tsx` 的身体矩形取自 `companion.scale / anchor` 与屏幕尺寸，**不根据人物检测结果放大**。live 的宽高比在首帧时读取。已有媒体日志反复显示 `768×1344`，但历史日志没有保存异常时刻的原始画面，不能仅凭这一点断言模型一定是根因。

若 Stage 的尺寸不变、raw 视频中人物占比增大，才可定位到上游生成构图 / 镜头变化；如果 raw 不变而窗口变大，应查 scale、屏幕与窗口坐标、用户缩放事件。Vidu 生成视频与 pi agent 的文本工具模型是两条链路。

### B. 抠像误删人物内部（已离线复现）

旧 `greenKey.ts` 的逻辑：

```text
g > max(r,b) + 3 → 视为可能绿幕
附近 3 像素没有不偏绿的邻居 → alpha = 0
```

一块 `rgb(183,198,178)` 的浅色衣服只有很轻微绿染，也会进这一分支。一旦区域宽于边缘搜索范围，中心直接被挖空。角色放大后离轮廓更远，更容易出现大块透明。

新旧真实 WebGL 对照确认：相同合成衣服区域，旧版中心 alpha=0，新版保持不透明；1.8 倍构图也通过。这证明本地算法有缺陷，但不等同于已复现用户当时完整的线上画面。

### C. 透明处出现另一个较小角色（截图线索，未确认唯一原因）

用户后续截图中，大角色躯干处可见较小角色的手 / 腿。合成截图不能区分原视频就画了两个人、待机层透出，还是多个应用窗口重叠。代码中确有 200ms 的交叉淡入淡出和缺少同 profile 单实例锁两项放大因素；现在分别消除，不把推测写成已定位根因。

## 2. 本次采用的分层方案

```text
模型侧：固定全身构图 / 位置 / 镜头 / 服饰 / 背景（尽力约束）
   ↓
实时帧 → 高置信度背景取样 → 背景连通性 / 衣物内部保护 → 立绘参照 + 构图 / 穿孔检查
   ├─ 正常：色键 + 边缘透明混合 + 去绿溢色 → GPU canvas
   └─ 异常：保留已上传的上一张纹理 → 持续异常显示 IdleLayer
                                               声音、字幕和会话继续
```

### 2.1 色键：不要把“略偏绿”当成“应该透明”

`keyColor.ts` / `greenKey.ts` 同用两个归一化量的较小值：

- 像素绿色超额量 / 当前背景绿色超额量；
- 像素相对绿色饱和程度 / 背景相对绿色饱和程度。

低于 0.30 视为前景，保留源 alpha 并按 `spill` 去绿染；高于 0.85 视为绿幕；中间区域尽可能用邻近前景做边缘混合。**找不到邻居时用连续的颜色置信度生成 alpha，不再直接删掉**。

新增 `foregroundMatte.ts` / `frameProbe.ts`：在最长边 160px 的缩略图上，从画面边界沿可能背景做四邻域洪泛。被确定前景包围的中等绿染区域，允许作为不透明衣物保留；与边界连通的背景阴影不获得此保护。低分辨率掩码包含确定前景，避免细小衣服印花造成采样空洞。GPU 再检查原分辨率邻近的真绿幕，保留真实内外边缘的连续 alpha；没有把 CPU 缩略图粗边界直接当成最终轮廓。

这不是“把人体轮廓以内全填白”：真正同背景色的手臂 / 腿间空隙仍然透明，边缘保留半透明。`keyTolerance / keyRadius / keySpill` 原字段不改名、不改默认值；不依赖用户把容差拉满才能避免大洞。

### 2.2 自动 key：可信取样，不盲目跟随

取左上 / 右上、左右中部四块小区域；每块至少 75% 明显偏绿、颜色较均匀，并且至少两块颜色一致才更新。被皮肤 / 浅色衣服盖住的样本不参加；相互矛盾的两组颜色不猜测。没有足够证据就保留上一 key。

首个可信 key 立即采用，后续更新平滑限速。被构图门控拒绝的帧不更新 key、不上传新纹理、不调整 canvas 内部分辨率。

### 2.3 构图保护：不让坏画面直接上屏

`framingGuard.ts`：每个新解码帧用最长边 **160px** 的缩略图估计前景面积和包围框。裁掉编码边框；包围框去掉每轴两端各 1% 的前景质量，避免孤立噪点影响。生产路径不逐帧读回全尺寸 WebGL alpha。

待机时从当前立绘离线计算参考几何；有效时优先使用它，避免第一张实时帧已经特写却被学习成正常。立绘不可用或不合理时，才用当前会话**第一个合理的实时帧**。不是不断跟随变化的移动平均；会话中修改立绘不会改变当前会话参考：

- 面积变为基线的 >1.7 倍，且宽 >1.25 倍或高 >1.2 倍：`zoom`。
- 几乎没有前景、相对面积骤降：`empty`；几乎整屏前景：`flood`。
- 以角色包围框高度 28%–62% 的上半身、前景质量中位横坐标附近取样；参考中心覆盖率 ≥0.75，而当前降至 <0.42：`matte-hole`。不取正常腿间空隙，也不以伸出的手决定中心。这是启发式异常保护，不是人体识别。
- 单纯挥手使包围框变宽、面积没有大涨：正常通过。
- 异常立即阻止新纹理上屏，短时重绘上一帧。
- 持续 ≥350ms：`fallback=true`，互斥切到本地待机；**构图保护本身不挂断、不自动重建付费会话**。坏帧后即使解码停止，rAF 仍推进被拒绝 geometry 的计时；不额外采样 / 上传，也不把旧好帧算作恢复。
- 连续正常 ≥400ms 后恢复实时画布，避免反复闪动。
- 每次新会话重置实时基线及计时，但保留该角色已加载的立绘参照；收纳 / 恢复不把异常构图重新学习成基线。

新增唯一共享配置字段：`CompanionVisualConfig.framingGuard?: boolean`，缺省开启。设置 → 显示 →「实时构图保护」可关闭，适用于确实想做大幅度表演的场景。只在 live 绿幕抠像开启时生效，不改变用户的桌宠 scale / anchor。

**这是展示降级保护，不是自动把放大的脸重新变回完整身体。** 已经裁出画面的头顶 / 脚无法凭后处理恢复。也不逐帧自动缩放人物，避免动作引起“呼吸式缩放”、脚底漂移。

### 2.4 生命周期与布局

- 待机、`<video>` 和 live `<canvas>` 绝对定位覆盖同一身体矩形；不让待机层把 live canvas 顶走。
- 去掉待机 / live 两个角色之间的交叉淡入淡出；待机退出立即 `display:none`，live 降级立即隐藏 canvas。透明边缘不能在切换时露出另一套肢体。源视频仍有下述 0.01 opacity 解码保活例外，它与可见 canvas 是同一个实时姿态。
- `onReady` 只在第一张被接受的纹理真正绘制后发出，不把创建 keyer 当作首帧就绪。待机 key 失败也不显示 raw 绿底；待机视频失败尝试立绘，仍失败则给不可用提示。
- main 在初始化配置 / runtime 前获取同 profile 单实例锁；再次启动只显示已有窗口。独立测试 profile 仍可运行；旧版没有锁，首次换包应先退出旧版，不能承诺自动清理旧进程。
- 继续用 rAF + 解码计数驱动视频抠像（透明 / 隐藏视频不能依赖 rVFC）；参数与尺寸变化也能触发重绘。
- Electron 支持的 `VideoFrame` 将一次解码结果固定用于取样、门控和纹理上传，避免检测了前一帧却上传后一帧；无论接受、拒绝或报错均 close。真实视频回归验证使用同一个快照及释放。没有该 API 的环境才退回原 video 路径。
- 保留 0.01 opacity 的视频避免 Chromium 过度降低解码频率；真实首帧和中途 2×2 占位帧要区分。
- shader 编译 / 链接、背景取样、纹理上传和 context loss 的错误能上报；live key 失败显示待机，不能退回大块绿色 raw 视频。
- stop 清理 GPU 对象、observer / timer / rAF，不主动丢失可复用 canvas 的 context。
- 画面降级时 UI 显示「画面保护中 · 声音继续」；独立的断流检测以新解码帧为准，不能因为 readyState=4 就清零计时：3s 待机、6s 重绑一次、20s 仍不恢复则挂断。声音本身也可能受网络影响，提示不是音频送达保证。

### 2.5 模型侧约束

`electron/vidu/config.ts` 在创建请求的 persona 后补充固定全身构图、不变焦、不特写、不走近镜头、不染绿服饰的约束。现有角色自定义 persona 也受益，**不改写用户存储的人设**；不添加未经确认的模型 API 参数。极长 persona 若没有剩余空间则不追加，避免超过现有 50000 字限制。

这只能降低漂移概率。后续三轮付费测试中，一轮完成约 8 分钟，两轮遇到停流，均未复现人物突然放大；不能据此证明模型始终遵从，详见 [真实测试报告](OPEN_SOURCE_REVIEW.md)。

## 3. 可观测性

每 5 秒 `GREENKEY stat`：source / canvas 尺寸、key 色、解码 / 上传计数、`fg`、`bbox`、`areaRatio`、`center`、guard reason。`FRAMING` 在状态转移时记录 accept / fallback / reason，也出现在设置的 Vidu 日志中。

这些数字不保存图像、密钥或 RTC token。它们能区分“编码尺寸改变”“人物内容占比变大”“抠像异常”“网络断流”，但最终诊断仍需 raw 与 alpha 对照。

复现命令与产物说明见 [HARNESS.md](HARNESS.md)。

## 4. 明确的限制 / 更进一步怎么做

- 没有用户异常时刻的原视频，所以还不能保证覆盖那一次问题的全部原因。
- 人物衣物如果真的与绿幕同色，纯色键无法可靠区分。不要盲目扩大半径或把所有洞填满；优先生成无绿色服饰、均匀背景的素材。
- 本保护不是语义人体分割，不会用只针对真人的模型裁掉牛头 / 角。有效立绘参照能拦截首帧特写；参照缺失、损坏、加载未完成或与预期构图不符时仍有漏检 / 误触。上半身倾斜、坐姿、跳舞也可能误触，开关可关闭。
- 连通性保护是保守补充：细轮廓在缩略图中消失、服装区域与背景连通时可能无法保护；纯绿服装不能凭空还原颜色。无法确认的巨大穿孔优先切待机，而非编造身体。
- 严重背景阴影 / 换色 / 服装重绘仍需真实 corpus 调阈值；不应承诺颜色算法能处理任意生成画面。
- 若真实 corpus 仍有不可区分的绿色服饰，下一步再评估适合动漫 / 写实角色的语义分割，配合背景连通性和边缘 matte；不要未经延迟与画质验证直接替换成重型模型。
- 持续构图异常只降级画面，计费仍继续；用户应手动挂断或等待现有 maxMinutes 上限。独立检测到解码停流 20s 时会挂断；两种机制都不自动创建第二个收费会话。
